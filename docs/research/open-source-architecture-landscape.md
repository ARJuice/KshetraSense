# Open-source architecture landscape for KshetraSense

**Reviewed:** 2026-10-11  
**Status:** comparative research and recommendations; no code or project architecture was changed.  
**Scope:** backend/data design, geospatial soil modelling, zoning, crop suitability, plant-disease ML, evaluation, and reproducibility. UI/UX is intentionally out of scope.

## Repository checkpoint

The plans/README still describe the application as pre-build, but the working tree inspected for this report contains a React/TypeScript mock-data frontend under `src/`, deterministic scenario/zoning/crop/leaf fixtures, a field-state test suite, and a placeholder field renderer with a typed interface. The current package manifest is frontend-only and has no Three.js/React Three Fiber dependency; this inspection found no Python backend source or trained `.keras`/`.h5` model artifact. Treat the real renderer, backend, clustering/rules, and model inference discussed below as proposed contracts and future work—not capabilities already implemented. This is a repository snapshot as of 2026-10-11, not a claim about code outside this checkout.

## Executive summary

No single open-source project found is a close technical equivalent to KshetraSense. The nearest GitHub application, CropSight, clusters satellite-derived NDVI and rainfall; it does not implement KshetraSense's soil-test feature schema, K-means/FCM result contracts, crop-neutral interpretation boundary, or shared MobileNetV3-Small leaf classifier. The more useful references are specialized: farmOS and ISO 28258 for durable agricultural/soil records, SoilGrids for digital-soil-mapping workflow and uncertainty, PyAEZ and CropSuite for the scope of real crop suitability, AgML for data/benchmark organization, and the PlantVillage/PlantDoc sources for image-data handling and external evaluation. ([CropSight](https://github.com/Priyam-28/CropSight), [farmOS API](https://farmos.org/development/api/), [ISO 28258 data model](https://github.com/ISRICWorldSoil/iso-28258), [SoilGrids 2.0 paper](https://soil.copernicus.org/articles/7/217/2021/), [PyAEZ](https://github.com/un-fao/pyaez), [CropSuite paper](https://gmd.copernicus.org/articles/18/1067/2025/), [AgML](https://github.com/Project-AgML/AgML), [PlantVillage metadata](https://github.com/spMohanty/PlantVillage-Dataset/blob/master/README_HF.md), [PlantDoc](https://github.com/pratikkayal/PlantDoc-Dataset)).

The best transferable ideas are **versioned data contracts and provenance**, **separate raw observations from gridded estimates and synthetic fixtures**, **recorded preprocessing and algorithm configurations**, **spatially appropriate validation**, and **crop-by-crop evidence with missing-input states**. None of these sources justifies turning K-means/FCM clusters or soil-only rules into a potato/tomato/apple cultivation-probability split. KshetraSense's current boundary—synthetic zoning, independent limited soil-compatibility factors, and a separate leaf classifier—remains the defensible one. ([FAO PyAEZ](https://www.fao.org/geospatial/data-and-tools/tools/python-package-for-agro-ecological-zoning-%28pyaez%29/en), [CropSuite methodology](https://gmd.copernicus.org/articles/18/1067/2025/), [current crop-suitability evidence note](crop-suitability-probability.md)).

## 1. Field-zone applications: use CropSight as a workflow specimen, not a validated template

CropSight describes a Streamlit application that selects a field by coordinates/radius, retrieves Sentinel-2 imagery through Google Earth Engine, computes NDVI, aggregates a median mosaic, clusters pixels, and combines zone statistics with a CHIRPS rainfall time series. Its README lists multiple algorithms, time-series views, comparisons, and report exports. These claims make it the closest repository-level *workflow* found, but its target signal is satellite vegetation condition, not pH/EC/NPK laboratory measurements or synthetic cell edits. ([CropSight README and technical workflow](https://github.com/Priyam-28/CropSight#technical-details), [setup and Earth Engine requirement](https://github.com/Priyam-28/CropSight#installation)).

**KshetraSense implication (assessment):** borrow the conceptual pipeline separation—input selection → feature derivation → clustering → per-zone summaries—only as a question to test against the TRD. Do not copy its feature semantics, recommendations, or external-data coupling. Its README is a repository owner's description, not independent evidence of methodological validity; this review did not execute it or find a peer-reviewed benchmark for it. The repository identifies an MIT license, but that is relevant only if code is ever reused; this report copies no code. ([repository and license metadata](https://github.com/Priyam-28/CropSight)).

## 2. Field observations and schemas: farmOS and ISO 28258

farmOS exposes farm records through JSON:API resources and uses JSON Schema to describe available resource types; the API also exposes server/API information and resource endpoints. Its client library fetches schemas so clients can work against server-supported record types. That is a practical reference for versioned, inspectable contracts and interoperability. farmOS itself is a Drupal-based farm-management application distributed under GPL-2.0, so its full stack is neither a direct architecture match nor a reason to adopt that dependency. ([farmOS API](https://farmos.org/development/api/), [farmOS.js schema flow](https://farmos.org/development/farmos-js/), [farmOS repository](https://github.com/farmOS/farmOS)).

The more soil-specific reference is ISRIC's open-source PostgreSQL implementation of the ISO 28258 domain model. Its documented concepts include a sampling project, site, plot, profile/profile element, specimen, property, procedure, observation, and result. This separates the *where*, *what material/layer*, *how measured*, and *measured value* instead of flattening all data into an unlabeled vector. ([ISRIC ISO 28258 repository and model concepts](https://github.com/ISRICWorldSoil/iso-28258)).

**KshetraSense implication (assessment):** retain the current compact `Scenario`/`Cell` model for synthetic demo interactions, but define a distinct future real-observation record before ingestion is implemented. At minimum, it should link a stable sample/observation ID to field/site and coordinates, collection time, soil depth, property, value/unit, analytical or sensor method, provenance, quality flags, and schema version. Keep raw observations separate from interpolation-derived cell values, user edits, and synthetic fixture values. The current TRD already records context for moisture and identifies missing values; ISO 28258 is evidence that sample/method/depth relationships matter more as the system moves beyond synthetic data. This is a design recommendation, not a claim that the demo needs a PostgreSQL schema today. ([ISO 28258 model](https://github.com/ISRICWorldSoil/iso-28258), [KshetraSense TRD](../TRD.md)).

farmOS's API/schema versioning also suggests a useful boundary even if KshetraSense remains local: make any future request/response contract explicitly versioned and keep service adapters separate from domain logic. The TRD appropriately leaves HTTP versus in-process execution open; the references reviewed do not establish that KshetraSense needs a remote API or database for the 216-cell demo. ([farmOS API](https://farmos.org/development/api/), [TRD](../TRD.md)).

## 3. Soil mapping: SoilGrids is a process reference, not a field-data source for this MVP

SoilGrids 2.0 predicts soil properties at 250 m cells and six standard depths using soil-profile observations plus hundreds of environmental covariates. Its published workflow includes data preparation, reproducible covariate selection, spatially stratified cross-validation, model tuning, final prediction, and quantile-regression-forest uncertainty estimates. The source data undergoes quality checks for coordinate/depth consistency, duplicates, accuracy, timestamps, analytical methods, and units. Those data-governance and validation stages are highly relevant patterns for any future KshetraSense real-soil pipeline. ([SoilGrids 2.0 paper](https://soil.copernicus.org/articles/7/217/2021/), [ISRIC SoilGrids documentation](https://docs.isric.org/globaldata/soilgrids/SoilGrids_faqs.html)).

There are important limits. ISRIC says SoilGrids is intended for global applications and is **not advised for local/farm-level use**. The official documentation also reported the v2 REST API temporarily paused, without a restoration timeline, at the time checked on 2026-10-11; it recommends stable alternatives such as Web Coverage Services/WebDAV for suitable use cases. SoilGrids data are under CC BY 4.0, but data licensing and citation still need to follow ISRIC policy. ([ISRIC use-scale guidance](https://docs.isric.org/globaldata/soilgrids/SoilGrids_faqs_04.html), [API status and access alternatives](https://docs.isric.org/globaldata/soilgrids/SoilGrids_faqs_02.html), [WCS documentation](https://docs.isric.org/globaldata/soilgrids/wcs.html)).

**KshetraSense implication (assessment):** borrow the pipeline's explicit data QA, feature/unit harmonization, spatial validation, versioned covariates, and uncertainty reporting. Do not populate the 18×12 demo with SoilGrids estimates or imply that 250 m pixels describe individual plot patches. For future field mapping, the project's planned held-out sample validation of IDW or alternatives is more appropriate than treating an interpolated raster as ground truth; any soil map should record source resolution, soil depth, analytical method, interpolation/model version, and uncertainty or validation error. ([SoilGrids 2.0 methods](https://soil.copernicus.org/articles/7/217/2021/), [ISRIC scale guidance](https://docs.isric.org/globaldata/soilgrids/SoilGrids_faqs_04.html), [TRD zoning section](../TRD.md)).

## 4. Crop suitability: PyAEZ and CropSuite explain why the current view must stay narrow

FAO's PyAEZ is an open-source Python implementation of Agro-Ecological Zoning. Its current repository organizes a workflow around input/scenario preparation, climate regime, crop simulation, climatic constraints, soil and terrain constraints, and integrated suitability/yield outputs; the FAO describes it as a tool for applying AEZ methods to local data. The components can be studied separately, but a complete assessment is a much broader modelling exercise than applying a few nutrient cutoffs. ([FAO PyAEZ overview](https://www.fao.org/geospatial/data-and-tools/tools/python-package-for-agro-ecological-zoning-%28pyaez%29/en), [PyAEZ source and module description](https://github.com/un-fao/pyaez)).

CropSuite is another open-source crop suitability model. Its paper describes crop-specific fuzzy membership functions across climatic, soil, terrain, and socioeconomic factors, with overall suitability determined using a limiting-factor/Liebig-minimum approach. It uses climate time series and crop-cycle/context parameters, and produces suitability classes/values, limiting factors, sowing/harvest windows, and recurrence of potential crop failure. The paper explicitly notes that crop suitability is difficult to validate and is not equivalent to agricultural yield or production. A 0–100 suitability value in such a model is a defined membership/suitability scale, not a calibrated probability that an individual field will succeed. ([CropSuite methods and evaluation limits](https://gmd.copernicus.org/articles/18/1067/2025/), [CropSuite source repository](https://github.com/flozabel/CropSuite)).

**KshetraSense implication (assessment):** the PRD's separation between crop-neutral clustering and independent crop-factor assessment is consistent with these frameworks' crop/use-specific logic. KshetraSense currently lacks several inputs used in broader suitability work—seasonal climate/water availability, crop/variety and management assumptions, texture, effective depth, drainage, and terrain. Keep unsupported factors as missing/“Not assessed”; do not borrow a fuzzy score, index, suitability class, or 100-point scale and relabel it “probability.” The project's existing crop-suitability evidence note already reaches this conclusion. ([CropSuite factor set and limitation discussion](https://gmd.copernicus.org/articles/18/1067/2025/), [PyAEZ](https://github.com/un-fao/pyaez), [KshetraSense crop-suitability research](crop-suitability-probability.md)).

### Useful, but not a drop-in library decision

PyAEZ is useful for understanding module boundaries and input dependencies. It is a larger GIS/crop modelling stack; its documented dependencies include NumPy, SciPy, GDAL, and Numba. CropSuite is a distinct scientific model, not a small rules engine. Before adopting either, the team would need a separate scope decision, relevant crop parameter provenance, target geography/production context, dependency/runtime assessment, and model validation plan. This report recommends neither as an MVP dependency. ([PyAEZ dependencies and modules](https://github.com/gicait/PyAEZ), [CropSuite paper](https://gmd.copernicus.org/articles/18/1067/2025/)).

## 5. Agricultural ML engineering: AgML as a reproducibility pattern

AgML is a centralized agricultural-ML framework that makes public datasets available across tasks and modalities, standardizes annotation structures, and provides dataset/benchmark discovery. Its documented formats distinguish image-classification labels, object boxes, and segmentation masks, and it exposes training-ready dataset objects. It supports both TensorFlow and PyTorch, so its value here is not model selection but how dataset identity, annotations, splits, and benchmark results can be made explicit. ([AgML repository](https://github.com/Project-AgML/AgML), [AgML dataset catalog](https://project-agml.github.io/datasets)).

**KshetraSense implication (assessment):** use a small manifest rather than importing the entire framework: dataset name/source/revision, license and access notes, file hashes or immutable snapshot ID, canonical class map, split/group manifest, preprocessing version, training configuration, and evaluation-artifact links. Preserve fixed MobileNetV3-Small as required by the PRD. Do not add AgML/PyTorch merely to imitate a broader benchmark platform. ([AgML repository and annotation workflow](https://github.com/Project-AgML/AgML), [KshetraSense PRD](../PRD.md)).

## 6. Leaf classifier data and model: PlantVillage, PlantDoc, and MobileNetV3

The PlantVillage repository's metadata README describes a 38-class dataset with a train/test split and a `leaf_id` field intended to keep images of the same physical leaf together. It also describes custom grouping by `leaf_id` to avoid leakage. KshetraSense uses a fixed 17-label subset (four apple, ten tomato, three potato classes), so the source folder names and class mapping should be audited against the actual pinned dataset revision before training. If using the supplied test split, verify it against the exact files/revision; if deriving a validation split, keep physical-leaf groups disjoint and do not use the held-out test set for model selection. ([PlantVillage dataset repository and split metadata](https://github.com/spMohanty/PlantVillage-Dataset/blob/master/README_HF.md), [KshetraSense PRD label plan](../PRD.md)).

PlantDoc was presented as a visual plant-disease dataset based on internet-scraped images, with 2,598 examples across 13 species and up to 17 disease classes. Its repository contains a cropped classification set and a separate object-detection dataset link, and reports CC BY 4.0. A currently open repository issue alleges train/test image overlap. That issue is an **unverified report**, not confirmation of a dataset defect; it is enough reason to hash/audit exact and near duplicates before treating PlantDoc as an independent external test. Its labels must be mapped conservatively to the KshetraSense 17 classes; unsupported classes should be excluded and class coverage reported. ([PlantDoc repository and dataset description/license](https://github.com/pratikkayal/PlantDoc-Dataset), [open duplicate-split issue](https://github.com/pratikkayal/PlantDoc-Dataset/issues/4), [PlantDoc paper](https://arxiv.org/abs/1911.10317)).

PlantVillage and PlantDoc are materially different data domains: controlled single-leaf backgrounds versus more varied internet/field-like imagery. Therefore, PlantDoc can be a cross-dataset stress test only after data quality, duplicates, and label semantics are audited; it is not automatically a representative sample of actual KshetraSense deployment users or phone images. The original PlantDoc paper and repository establish the dataset's source/annotation context, but not the field validity of a particular MobileNetV3-Small model. ([PlantVillage metadata and paper citation](https://github.com/spMohanty/PlantVillage-Dataset/blob/master/README_HF.md), [PlantDoc paper and repository](https://arxiv.org/abs/1911.10317), [PlantDoc dataset repository](https://github.com/pratikkayal/PlantDoc-Dataset)).

For Keras MobileNetV3, preprocessing is an easy source of silent mismatch: with the default `include_preprocessing=True`, the model contains a rescaling layer and expects float pixel inputs in `[0,255]`; the documented `preprocess_input` is then a pass-through. If preprocessing is disabled, the expected range changes to `[-1,1]`. Store the exact image size, channel/color order, pixel range, model config, class map/version, and preprocessing setting with the model artifact, and test the serving path against the training path. ([TensorFlow MobileNetV3Small API](https://www.tensorflow.org/api_docs/python/tf/keras/applications/MobileNetV3Small), [Keras MobileNet documentation](https://keras.io/api/applications/mobilenet/)).

TensorFlow's transfer-learning guidance uses a frozen pretrained base with a new classification head, then optionally fine-tunes selected/all layers at a low learning rate. It specifically cautions that BatchNormalization layers should remain in inference mode while fine-tuning. This fits the project's fixed-backbone transfer-learning plan, but is a training recipe to evaluate—not a claim of measured performance. ([TensorFlow transfer-learning tutorial](https://www.tensorflow.org/tutorials/images/transfer_learning), [Keras transfer-learning guide](https://www.tensorflow.org/guide/keras/transfer_learning)).

**KshetraSense implication (assessment):** keep leaf inference as a separately versioned module with an image-only request. A model result should bind the model artifact, preprocessing version, class-map version, input dimensions, inference timing, and evaluation report; crop/zone/soil UI context must remain outside the tensor input. The PRD already requires this isolation and transient image handling. ([KshetraSense PRD](../PRD.md), [MobileNetV3 API](https://www.tensorflow.org/api_docs/python/tf/keras/applications/MobileNetV3Small)).

## 7. Zoning algorithms and validation

The scikit-learn `KMeans` API takes a samples-by-features matrix, exposes `random_state`, and supports repeated initialization through `n_init`. Its current documentation states that `n_init='auto'` can mean only one run with `k-means++`; record an explicit `n_init` and seed rather than relying on library defaults that can change across versions. ([scikit-learn KMeans API](https://scikit-learn.org/stable/modules/generated/sklearn.cluster.KMeans.html)).

The scikit-fuzzy `cmeans` API uses a features-by-samples matrix and returns a fuzzy membership matrix, so an adapter must carefully transpose inputs/outputs relative to scikit-learn's convention. Membership is assignment strength among clusters, not calibrated probability or model confidence. ([scikit-fuzzy `cmeans` API](https://scikit-fuzzy.readthedocs.io/en/latest/api/skfuzzy.cluster.html), [FCM example and fuzzy partition coefficient](https://scikit-fuzzy.readthedocs.io/en/latest/auto_examples/plot_cmeans.html)).

Silhouette analysis is a feature-space cohesion/separation diagnostic; it does not establish geographic contiguity, agronomic usefulness, or crop suitability. KshetraSense's planned synthetic recovery benchmark, seed/noise stability, contiguity, and minimum-zone-size checks are therefore important complements rather than redundant metrics. If a later implementation merges spatially adjacent clusters, keep it as an explicit recorded post-processing step, not hidden behavior inside the clustering method. ([scikit-learn silhouette analysis](https://scikit-learn.org/stable/auto_examples/cluster/plot_kmeans_silhouette_analysis.html), [KshetraSense TRD diagnostics](../TRD.md)).

**KshetraSense implication (assessment):** persist an immutable zoning-run manifest with scenario/revision, input fingerprint, included feature order and units, missing/incomparable exclusions with reasons, normalization parameters/version, method/library version, `k`, FCM exponent where applicable, explicit seed/initialization settings, timings, assignments, centers, membership matrix, zone summaries, adjacency, diagnostic values, and any separate merge configuration. The current TRD specifies most result semantics; adding a stable input fingerprint and exact library/runtime version would make a run easier to reproduce after fixtures or dependencies change. This is a recommendation for future implementation, not a TRD edit. ([scikit-learn KMeans API](https://scikit-learn.org/stable/modules/generated/sklearn.cluster.KMeans.html), [scikit-fuzzy FCM API](https://scikit-fuzzy.readthedocs.io/en/latest/api/skfuzzy.cluster.html), [TRD](../TRD.md)).

## Architecture and implementation lessons for the existing plan

These are research-derived refinements to consider when implementation starts. They do **not** alter the current stack or approved scope.

1. **Keep one canonical domain layer and thin adapters.** Keep scenario/cell/edit history, feature validation, normalization, clustering, crop rules, and image inference as distinct modules with stable input/output types. Add a transport adapter only after latency, model size, and local deployment needs resolve the TRD's open HTTP-versus-in-process choice. For a 216-cell, seven-feature demo, the important complexity is semantic correctness and provenance rather than distributed scaling; this is an assessment from KshetraSense's documented dimensions, not a claim from the referenced projects. ([TRD](../TRD.md), [farmOS schema/API pattern](https://farmos.org/development/api/)).
2. **Make source type and derivation first-class.** Preserve separate values for synthetic fixture data, direct soil observations, user edits, interpolated/model estimates, and prepared demo outputs. Keep measurement method, units, depth, time, and missingness explicit. The soil-schema and SoilGrids references demonstrate why these fields affect comparability and validation. ([ISO 28258 model](https://github.com/ISRICWorldSoil/iso-28258), [SoilGrids methods](https://soil.copernicus.org/articles/7/217/2021/)).
3. **Treat every algorithm result as an auditable artifact.** Store exact inputs or immutable fixture references plus input hashes, schema and preprocessing versions, configuration, random seeds, dependency versions, and diagnostics. Keep zoning sample fixtures in a different type from actual production results, as Decision 0002 already requires. ([AgML reproducibility/data conventions](https://github.com/Project-AgML/AgML), [KshetraSense Decision 0002](../decisions/0002-mock-data-demo-first.md)).
4. **Validate spatial claims spatially.** Synthetic planted zones can supply known labels for recovery metrics; real field mapping needs spatially appropriate holdouts and measured-sample validation rather than random-cell splits alone. SoilGrids uses spatial stratification for a global mapping task; that does not dictate the exact KshetraSense scheme, but it illustrates why spatial dependence matters. ([SoilGrids methods](https://soil.copernicus.org/articles/7/217/2021/)).
5. **Keep rules and supervised models semantically separate.** A source-backed factor/rule result, FCM membership, calibrated classifier probability, and crop-success probability are different kinds of quantities. Return explicit class/factor/reason and uncertainty semantics instead of a generic `score` field. ([PyAEZ](https://github.com/un-fao/pyaez), [CropSuite methodology](https://gmd.copernicus.org/articles/18/1067/2025/), [scikit-fuzzy FCM](https://scikit-fuzzy.readthedocs.io/en/latest/api/skfuzzy.cluster.html), [KshetraSense probability note](crop-suitability-probability.md)).
6. **Do not add infrastructure just because comparables have it.** farmOS's Drupal/JSON:API stack, SoilGrids' raster services, and CropSight's Earth Engine pipeline solve different deployment/data problems. KshetraSense can keep its local browser plus proposed local Python modules until actual persistence, import volume, concurrency, or model-serving measurements establish a need for a database/API boundary. ([farmOS repository](https://github.com/farmOS/farmOS), [SoilGrids access guidance](https://docs.isric.org/globaldata/soilgrids/SoilGrids_faqs_02.html), [CropSight](https://github.com/Priyam-28/CropSight), [TRD](../TRD.md)).

## Gaps to resolve during implementation

- **Pin/audit datasets before training:** record the exact PlantVillage revision and file manifest; confirm the 17 intended folders, label spellings/counts, group IDs, and split separation. Create validation groups only within training data and reserve the test split for final evaluation. ([PlantVillage metadata](https://github.com/spMohanty/PlantVillage-Dataset/blob/master/README_HF.md)).
- **Audit external PlantDoc data:** deduplicate exact and near-identical images across splits; inspect class names and label semantics; calculate the actual supported-class intersection; report coverage and results separately. The open duplicate issue is a lead for this audit, not a verified conclusion. ([PlantDoc repository](https://github.com/pratikkayal/PlantDoc-Dataset), [issue #4](https://github.com/pratikkayal/PlantDoc-Dataset/issues/4)).
- **Freeze model serving semantics:** choose one MobileNetV3 input-preprocessing path and write a test that training and inference produce identical model input tensors from the same image. Track the 17-label map and model artifact as one versioned release. ([TensorFlow MobileNetV3Small API](https://www.tensorflow.org/api_docs/python/tf/keras/applications/MobileNetV3Small)).
- **Bound crop-profile meaning:** define geography, crop/cultivar, season, soil-test context, and management before publishing numeric thresholds; keep absent factors unassessed. Broader suitability or probability work requires its own data and evidence scope. ([PyAEZ](https://github.com/un-fao/pyaez), [CropSuite](https://gmd.copernicus.org/articles/18/1067/2025/), [crop-suitability note](crop-suitability-probability.md)).
- **Resolve the future service topology with evidence:** benchmark local model size/latency and installation needs before choosing an API/runtime. SoilGrids' current paused REST service is a caution against making an external service a required runtime dependency, not a reason to select a different vendor. ([ISRIC API status](https://docs.isric.org/globaldata/soilgrids/SoilGrids_faqs_02.html), [TRD open decisions](../TRD.md)).
- **Use actual algorithm diagnostics, not fabricated UI values:** pin algorithm versions/configuration and calculate metrics only for executed runs. Prepared fixtures remain labeled examples, not outputs of the live engine. ([scikit-learn KMeans](https://scikit-learn.org/stable/modules/generated/sklearn.cluster.KMeans.html), [scikit-fuzzy FCM](https://scikit-fuzzy.readthedocs.io/en/latest/api/skfuzzy.cluster.html), [Decision 0002](../decisions/0002-mock-data-demo-first.md)).

## Bottom line

Use these projects to sharpen KshetraSense's contracts, data-quality gates, uncertainty handling, and validation plan—not to recreate another application's stack. Keep the current local-first architecture proposal and fixed MobileNetV3-Small model intact until measured implementation evidence calls for a change. The strongest near-term additions are dataset pinning/deduplication checks, explicit run fingerprints/runtime versions, and a future soil-observation schema that preserves method/depth/provenance. Keep crop suitability independent per crop and keep any cultivation probability out of scope until a defined outcome dataset and independent calibration evidence exist. ([TRD](../TRD.md), [PRD](../PRD.md), [crop-suitability research](crop-suitability-probability.md)).
